# Version Tracking — Design Spec
**Date:** 2026-08-04
**Status:** Approved
**Scope:** Reliable build provenance baked into the artifact (version, commit hash, dirty
flag, build date) plus a new `-Version` CLI switch to query it on a single machine. No
existing tool's behavior changes.

---

## Background

The toolkit already has a version-bump convention: `build.ps1`'s `-Version` param default is
manually bumped and a matching git tag is cut (`v9.0.0`, `v9.0.1`, `v9.0.3`, `v9.1.0`). That
convention is only as reliable as the human running it — nothing stops a build with a stale
or unbumped `-Version`, and nothing lets you tell, on a machine you're troubleshooting,
whether the deployed `NMMTools.ps1` actually matches what the version string claims. With many
machines running copies built at different times via PDQ, this makes "do we have the latest
version on this box" unanswerable without diffing file contents by hand.

This spec covers single-machine version verification only. Fleet-wide auditing (e.g. querying
many endpoints via PDQ Inventory) is an explicit non-goal, deferred until a trustworthy
per-machine version query exists to build on.

---

## Build-time changes (`build.ps1`)

1. Capture the commit the artifact is built from:
   `git -C $root rev-parse --short HEAD`. If git is unavailable or the command fails, fall
   back to `'unknown'` rather than failing the build.
2. Detect a dirty working tree: `git -C $root status --porcelain`. If non-empty, append
   `-dirty` to the commit hash (e.g. `a1b2c3d-dirty`) — an unambiguous signal that this build
   doesn't correspond to any committed state.
3. Capture the build timestamp once into a variable and reuse it for both the existing header
   comment and the new version block below, so the two can't drift apart.
4. Extend the existing header comment to include the commit hash, e.g.:
   `# NMM System Toolkit v9.1.0 (a1b2c3d) | built 2026-08-04 10:00 | GENERATED by build.ps1 - DO NOT EDIT`
5. Inject a new source block immediately after the param block (which must remain the first
   statement in the artifact) and before the core region:
   ```powershell
   $script:ToolkitVersion   = '9.1.0'
   $script:ToolkitCommit    = 'a1b2c3d'
   $script:ToolkitBuildDate = '2026-08-04 10:00'
   ```
   These are real script variables, not comments, so they're readable at runtime.

None of this changes the existing `-Version` build param mechanism (still a human-set release
label) or the tag-per-release convention — it adds a tamper-evident layer underneath it.

## Runtime changes

- `src\entry\00-param.ps1`: add `[switch]$Version`.
- `src\entry\99-main.ps1`: handle `-Version` first, before mode selection, `-ListTools`, and
  `-Tool` — it's the simplest, lowest-risk path and shouldn't depend on anything else in the
  entry point succeeding first.
  ```powershell
  if ($Version) {
      Write-ToolOutput ('NMM System Toolkit v{0}' -f $script:ToolkitVersion) -Level Info
      Write-ToolOutput ('Commit: {0}' -f $script:ToolkitCommit) -Level Info
      Write-ToolOutput ('Built: {0}' -f $script:ToolkitBuildDate) -Level Info
      exit 0
  }
  ```
  Using `Write-ToolOutput` (never `Write-Host`) means the version banner is also captured to
  the session log when `-LogPath` is supplied, consistent with every other output path, and
  keeps this on the same Console/GUI/Capture sink routing as the rest of the toolkit.
- No registry entry needed — this is a toolkit-level flag, not a dispatched tool, matching how
  `-ListTools` is already handled.

---

## Non-goals (explicit)

- No live comparison against GitHub or any other "latest version" source. `-Version` prints
  what's baked in; comparing against the latest tag/release is a manual step for now.
- No fleet-wide query mechanism. A future PDQ Inventory-based audit can shell out to
  `NMMTools.ps1 -Version` once this exists, but building that audit is out of scope here.
- No change to how the release version number itself is chosen (still the manual `build.ps1
  -Version` param + git tag convention) — only the commit hash and dirty flag are new.
- No warning/precedence logic for combining `-Version` with `-Tool` or `-ListTools` — `-Version`
  simply wins and exits first if present, mirroring the simplicity of the flag itself.

---

## Testing

- Extend `tests\artifact.tests.ps1` (same pattern already used for `-ListTools`/`-Tool`): run
  the built artifact with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File $script:Artifact
  -Version`, assert `$LASTEXITCODE -eq 0`, and assert the output matches the version/commit
  pattern (e.g. `-Match 'NMM System Toolkit v'` and `-Match 'Commit:'`).
- `.\build.ps1` then `Invoke-Pester .\tests` — full suite, same as every prior change.
- Manual smoke test: run `.\build.ps1` with a clean tree and confirm the commit hash has no
  `-dirty` suffix; make an uncommitted edit and rebuild to confirm the suffix appears.
